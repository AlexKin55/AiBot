# Протокол взаимодействия с роботом по WebSocket

> Готовый клиент на Python3 (FastAPI) для управления роботом и приёма аудио:
> каталог `~/Work/AiServer` (README, requirements). Ниже — спецификация
> протокола.

Робот (M5Stack CoreS3) подключается к серверу как **WebSocket-клиент**:
`ws://WS_HOST:WS_PORT/WS_PATH` (значения из `config/config.h`,
по умолчанию `ws://192.168.1.8:9001/`).

Транспорт — **текстовые фреймы** для команд и **бинарные фреймы** для аудио
(см. разделы «RECORD — запись по голосу (VAD)» и «Воспроизведение аудио»).

Ключевые слова команд регистронезависимы. Пробелы внутри аргументов не
допускаются. Каждая команда завершается либо подтверждением `ACK`, либо
ошибкой `ERR`. Исключение — VAD-команды `RECORD:start`/`RECORD:stop`,
которые **робот шлёт серверу сам** (ответов не требует).

## Команды (сервер → робот)

### PING
Запрос живого соединения.

```
PING
```
Ответ: `PONG:<uptime_ms>`

### EMOTION — вывод эмоций на экран
Задать выражение лица (аватар M5Stack-Avatar).

```
EMOTION:<name>
```
`name` ∈ `neutral | happy | angry | sad | doubt | sleepy`

Примеры:
```
EMOTION:happy
EMOTION:sleepy
```
Ответ: `ACK:EMOTION:<name>` / ошибка: `ERR:EMOTION:unknown emotion`

### MOVE — движение головы (пан-тилт)
Поворот относительно текущего положения или возврат в центр.

```
MOVE:left:<degrees>
MOVE:right:<degrees>
MOVE:up:<degrees>
MOVE:down:<degrees>
MOVE:center
```

Примеры:
```
MOVE:left:45
MOVE:up:30
MOVE:center
```
Ответ: `ACK:MOVE:left:45` (или `ACK:MOVE:center`) /
ошибка: `ERR:MOVE:invalid move`

### LED — подсветка (светодиоды на голове)
```
LED:<r>,<g>,<b>
```
`r,g,b` — 0..255.

Пример:
```
LED:255,0,0
```
Ответ: `ACK:LED:255,0,0` / ошибка: `ERR:LED:invalid color`

### RECORD — запись по голосу (VAD, робот — инициатор)

В состоянии `ready` робот постоянно слушает микрофон и оценивает уровень
шума. При резком увеличении громкости (голос) он **сам** шлёт серверу:

```
RECORD:start
```

и начинает передавать **PCM-чанки** (кодек 1):

```
byte[0]   = 1   (тип: AUDIO)
byte[1]   = 1   (кодек: PCM)
byte[2..] = сырые сэмплы int16 LE (16 кГц, моно)
```

Один PCM-сэмпл — 16 бит; секунда звука — 32 000 байт (16 кГц × 2).
Чанк накапливается ~`MIC_AUDIO_CHUNK_SECONDS` (1 с) и отправляется одним
бинарным фреймом. Завершение сегмента — по тишине (`VAD_SILENCE_MS`, 900 мс)
или таймауту (`VAD_MAX_SEGMENT_MS`, 5 с); после этого робот шлёт:

```
RECORD:stop
```

и досылает последний неполный чанк. Сервер собирает все чанки, сохраняет
запись, ретранслирует аудио в Yandex (STT -> GPT -> TTS) и озвучивает ответ
роботу **PCM-чанком codec 1** (см. «Воспроизведение аудио»).

Параметры VAD — в `config/config.h`: `VAD_MIN_THRESHOLD`,
`VAD_NOISE_ADAPT`, `VAD_START_HANGOVER_FRAMES`, `VAD_SILENCE_MS`,
`VAD_MAX_SEGMENT_MS`.

## Воспроизведение аудио (сервер → робот)

Сервер может отправить роботу аудио для воспроизведения в динамике теми же
бинарными фреймами. Единственный формат — **PCM (codec 1)**, тот же, что
робот шлёт серверу:

```
byte[0]   = 1              (тип: AUDIO)
byte[1]   = 1              (кодек: PCM)
byte[2..] = сырые сэмплы int16 LE (16 кГц, моно)
```

При получении такого фрейма робот воспроизводит его в фоновой задаче
`playbackTask` (стек 32 КБ) одним непрерывным буфером. Если в этот момент
робот слушает микрофон (VAD/запись), он останавливает его (динамик и
микрофон делят I2S-ресурсы на CoreS3), а после окончания воспроизведения
снова переходит к прослушиванию.

## Ответы (робот → сервер)

| Формат | Назначение |
|--------|-----------|
| `ACK:<COMMAND>[:args]` | команда выполнена успешно |
| `ERR:<COMMAND>:<reason>` | команда отклонена (неверные аргументы / неизвестная команда) |
| `PONG:<uptime_ms>` | ответ на `PING` |
| `RECORD:start` | VAD: робот определил речь и начал слать PCM-чанки |
| `RECORD:stop` | VAD: тишина/таймаут — сегмент завершён (после него — последний чанк) |
| `HB` | heartbeat каждые 15 с (см. ниже) |

## Heartbeat (HB)

Робот в состоянии `READY` шлёт текстовый фрейм `HB` каждые
`WS_HEARTBEAT_INTERVAL_MS` (по умолчанию 15 с). Цель — держать канал живым:
роутер/NAT сбрасывает TCP-сессию, простаивающую ~2 минуты, из-за чего сервер
не может достучаться до робота при долгой обработке (STT → GPT → TTS).
Сервер **только логирует** `HB` и **не обрывает** соединение, если HB
перестал приходить (online/offline определяется фактом соединения).

## Пример сессии

**Управление (сервер → робот):**
```
сервер → PING
робот  → PONG:120345

сервер → EMOTION:happy
робот  → ACK:EMOTION:happy

сервер → MOVE:left:45
робот  → ACK:MOVE:left:45

сервер → MOVE:center
робот  → ACK:MOVE:center

сервер → LED:0,255,0
робот  → ACK:LED:0,255,0

сервер → FOOBAR
робот  → ERR:COMMAND:unknown command
```

**Голосовой цикл (VAD, робот — инициатор):**
```
робот  → RECORD:start
(робот шлёт бинарные PCM-чанки [тип=1][кодек=1][pcm int16 LE])

робот  → RECORD:stop
(робот досылает последний неполный чанк)

(между сообщениями, пока сервер обрабатывает STT->GPT->TTS, робот продолжает
 слать HB каждые 15 с — канал не умирает от простоя)

сервер → [бинарный PCM-чанк [тип=1][кодек=1][pcm]]  (ответ STT->GPT->TTS)
```

## Реализация

- Модуль протокола: `src/protocol/protocol.{h,cpp}` (парсер + формирование ответов).
- Приём и исполнение команд: `src/aibot/main.cpp` → `onWsMessage()` →
  `protocol::parse()` → `handleCommand()` → подсистемы
  (`EspScreen`, `EspMovement`, `EspLeds`) с отправкой `ACK`/`ERR`.
- Аудио (VAD-запись и озвучка): `src/aibot/commands.cpp` (`tickVad`,
  `sendAudioChunk`, `playbackTask`) + сервер `~/Work/AiServer`.
